# 上海迪士尼 · 连续采集验收

独立 GitHub Actions 云端测试，不依赖用户 Mac，不涉及小程序开发。

## 为什么改版

11 月 11 日的旧版每五分钟 cron 只成功采集两轮（计划 156 轮），另有夜间延迟触发。因此不再把每轮请求依赖于 GitHub 调度。历史运行与 Artifacts 保留，旧版样本仅作前期参考，不计入新版验收。

## 新版时间

全部为上海当地时间 UTC+8：

| 日期 | 时段 | 用途 |
|---|---|---|
| 2026-11-12 | 部署后至 21:30 | 恢复测试，不计入正式双日验收 |
| 2026-11-13 | 08:30–21:30 | 正式第一天 |
| 2026-11-14 | 08:30–21:30 | 正式第二天 |

按目前公布时间，正式目标 26 个营业小时、312 个五分钟采样时段。12h 检查点 11 月 13 日 20:30；24h 检查点 11 月 14 日 19:30；最终 26h 检查点 11 月 14 日 21:30。若闭园时间变化，更新配置。

## 架构

- GitHub 只负责启动当天的任务链，而非每五分钟启动一次任务；每天有多次备用启动时间。同一工作流禁止并行，已运行任务不会因新 schedule 被取消。GitHub 仍不保证启动或任务接续准时。
- 三个顺序执行的 runner 段：08:30–13:00、13:00–17:30、17:30–21:30。单段最多 4.5 小时，第一段可提前最多 45 分钟等待开园。
- `continuous.py` 自己每五分钟采样，按墙上时钟时段对齐。晚启动立即采当前时段，绝不补造过去样本。失败也独立记录，并继续下一轮。
- 原始响应与报告存入各个唯一采样目录，不覆盖旧样本。每段输出 `samples.jsonl` 和 `segment_summary.json`，结束后上传 Artifacts 保留 7 天。运行期间日志输出 `SAMPLE` 行便于确认采样。
- 截止 11 月 14 日 21:30 后禁止上游请求，最后一个工作流尝试自动停用定时触发。

## 验收

逐日去重统计实际五分钟时段覆盖率、最长采集间隔、两个源各自成功率、两源同一轮分钟数完全一致率/五分钟内一致率、状态一致率及变化。不能把两源相互一致当作官方 App 一致。官方对照仍须另行采集同步读数。

GitHub 的备用触发仍可能被延迟或跳过，因此即使本架构改善，也不能保证每天完整启动。最终以实际日志及原始数据验收，不够 24 个有效运营小时则继续补测。

## 文件

- `config.json`：营业窗口、恢复日与正式验收日
- `monitor.py`：单次请求、原始数据、逐项比对、营业时间保护
- `continuous.py`：持续循环、样本归档、失败记录和分段汇总
- `.github/workflows/shanghai-disney-24h.yml`：连续分段工作流
